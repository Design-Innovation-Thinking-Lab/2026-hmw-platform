# 三個分析模式的差異比較

> 對照 `migrations/bundle/02_run_second.sql` 裡三個模式的**實際 prompt_template 全文**整理，不是只看步驟標題猜的。步驟數與 scope 的總表見 `docs/generation-logic.md` 第三節；這份文件專注在「每個模式實際要求 AI 怎麼思考、用什麼框架、輸出什麼格式」的差異。

## 一句話總結

- **領航員**：紮根理論式逐字稿編碼（6R/4R 框架），每份逐字稿先各自跑完一條編碼鏈，最後才合併——最嚴謹、最貴、最慢。
- **教練**：跳過逐字稿個別編碼，直接進整體歸納（Findings → Summary → Insight），中間插一道「AI 自我審視」做自我校正——比領航員快，但個別受訪者的編碼軌跡沒那麼完整。
- **建築師**：唯一引入「體驗維度／知覺價值」「服務創新三環（Desirability/Feasibility/Viability）」這類設計方法論框架，且全程用詳盡的檢核清單規範輸出格式——4 步最精簡，但格式要求反而是三者中最嚴格的。

## 二、逐模式拆解

### 領航員 HumanAI框架（8 步）

見 `docs/analysis-steps-guide.md`，這份文件已經寫得很完整：6R 框架做開放編碼、4R 框架做主軸編碼、JTBD 句型「當 [情境] 時，我想要 [需求]，以便/因為 [結果]」、每個 JTBD/HMW 都強制要求列出**所有**支持的原話來源（不能只列一句）。這裡不重複。

### 教練 HumanAI框架（7 步，全 collective）

| 步驟 | 實際要求 AI 做什麼 |
|---|---|
| 1. 整理Findings | 明確要求 **Bottom-up**：「只記錄受訪者說了什麼、做了什麼、感受到了什麼，不要進行任何『為什麼』的推論」；每個 Finding 要「原子化」（獨立完整）；輸出格式是三欄表格（提問+timestamp \| 原始引言+timestamp \| Findings） |
| 2. Summary | 固定依四大類整理：①研究主題使用現況與偏好 ②使用者需求與核心痛點 ③AI功能應用與挑戰 ④對未來的想像與期待；要求「凸顯概念差異對比」「找出相似處」 |
| 3. Insight | 明確要求對應到**三個寫死在 prompt 裡的研究目標**（了解現況／了解困難點／了解建議與未來期望）——這三個目標是**固定文字**，不會因為你在研究室填的「研究目的」而變（系統另外會把研究室實際的研究主題/目的注入到 system prompt，但這一步自己的 prompt_template 內容本身是通用版、不是客製化的） |
| 4. **AI 自我審視** | 三個模式裡**唯一**有這一步——明確要求 AI「再次審視步驟1、2、3的分析資料是否皆出自所有受訪者逐字稿？是否有不一致或過度推論的地方？」，等於系統內建一次自我校正，不靠人工重讀 |
| 5. 統整全部訪談Insight | 把每位受訪者的 Insight 合併，要求保留「對應每一洞察的逐字稿」以便追溯 |
| 6. 總Insight產出JTBD | 明確點名套用學術框架：**Clayton Christensen、Alan Klement 的「需求三層模型」（Three Levels of Jobs）** |
| 7. 產出HMW | 要求每個 HMW 都附上對應的 JTBD 句型作為支撐 |

**跟領航員的關鍵差異**：領航員是「先逐份逐字稿個別編碼，最後才合併」；教練是**一開始就合併處理**，沒有個別受訪者各自先跑過一輪編碼的中間產物。優點是快（少了 5 個 individual 步驟），缺點是少了「每位受訪者獨立編碼結果可以互相比對」這層嚴謹度——但多了「AI 自我審視」這道領航員沒有的校正機制來部分彌補。

> ⚠️ **一個小細節**：步驟 1、2、6 的 prompt 文字裡**直接寫「請幫我整理成附圖截圖一樣產出表格」「以附圖為例」「請以附圖JTBD的架構」**——這些「附圖」就是 `docs/SETUP.md` 步驟 12 提到、沒有被 migration 帶過來的範例圖。所以這三步並不是完全不受影響：AI 看不到「附圖」長什麼樣，只能純靠文字描述推測格式，輸出品質可能跟 Jintin 原本示範的不會一模一樣（但不會壞掉，AI 還是會依文字指示產出合理的表格）。如果你發現教練模式這三步的輸出格式怪怪的，重新上傳對應的範例圖就是最直接的改善方式。

### 建築師 HumanAI框架（4 步，1 個 individual + 3 個 collective）

| 步驟 | 實際要求 AI 做什麼 |
|---|---|
| 1. [T01]研究背景與資料定義（individual） | **唯一**明確定義「體驗維度」（使用者互動中感受到的不同面向）跟「知覺價值」（使用者主觀認為獲得的效益）這兩個分析鏡頭，後面三步都會回扣這兩個概念。Prompt 裡也寫了「請保持 human in the loop」「每一步驟時請先停下來想一想」——**但這只是寫給 AI 看的行為指示，不是系統真的會在步驟之間暫停等人工確認**；實際執行時 `runAnalysisFlow()` 是連續跑完 4 步，不會因為這句話真的停下來（除非你在 `/admin/steps` 把某步設成 `is_active=false`，或之後自己改程式加人工關卡） |
| 2. [T02]受訪者編碼與資料預處理Findings（collective） | 三者中**格式要求最詳盡**的一步：給了完整的 Finding 撰寫檢核清單（資訊識別優先序、顆粒度要求、結構化模板「觀察事實／分析要點／知識標籤」、甚至規定 metadata 要怎麼標註 `id/timestamp/category/confidence/related_findings`）——比較像是在教 AI 照一套嚴謹的知識管理規範寫筆記，不只是歸納重點 |
| 3. [T03]輸出結果任務定義JTBD（collective） | 標準 JTBD 萃取（句型：`When {context}, I want to {job} because {motivation}, so I can {outcome}`），但**多了一段領航員、教練都沒有的「關聯性分析」**——要求把每個 JTBD 回扣到步驟 1 定義的「體驗維度」與「知覺價值」，分析兩者的對應關係 |
| 4. [T04]JTBD轉HMW（collective） | **唯一**要求套用「服務創新三環」框架——每個 HMW 要盡量涵蓋 **Desirability（需求性）／Feasibility（技術可行性）／Viability（商業可行性）**三個面向，比純粹「使用者需求出發」的 HMW 多了技術與商業可行性的考量 |

**跟另外兩個模式的關鍵差異**：建築師是唯一引入「體驗維度／知覺價值」「服務創新三環」這類**設計方法論框架**的模式（不是純質性研究的編碼框架），且唯一要求把 JTBD 回扣到一個自訂的分析鏡頭上。4 步最少、跑最快，但第 2 步的格式規範其實是三個模式裡最嚴格、最像在建立一套可重複使用的知識庫規範。

## 三、怎麼選

| 情境 | 建議 |
|---|---|
| 要給老師/口試委員看完整編碼軌跡、每個決策都要能回溯 | **領航員**——個別受訪者編碼 + 主軸/選擇性編碼都是完整留存的中間產物 |
| 時間有限，要快速拿到洞察跟 HMW，不需要逐字稿級的編碼細節 | **教練**——少了個別編碼的 5 步，而且有自我審視機制兜底 |
| 研究主題偏產品/服務設計，想從一開始就用「體驗維度」「商業可行性」這種設計方法論框架切入，而不是純學術質性研究框架 | **建築師**——唯一內建這些設計思考框架的模式 |
| 只是想先測試整條鏈路能不能跑（例如第一次架設環境時） | **建築師**——4 步最少，跑最快，API 花費也最低 |
