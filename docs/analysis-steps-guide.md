## 可用模板變數

在 prompt template 中，您可以使用以下 Nunjucks 模板變數：

### 基礎變數
| 變數 | 說明 | 適用範圍 |
|------|------|----------|
| `{{ transcript }}` | 當前逐字稿完整內容 | Individual 步驟 |
| `{{ filename }}` | 當前檔案名稱 | Individual 步驟 |
| `{{ file_meta }}` | 檔案元資料 (上傳者、建立時間等) | Individual 步驟 |

### 跨步驟結果變數
| 變數 | 說明 | 適用範圍 |
|------|------|----------|
| `{{ previous_step_result }}` | 上一步驟的分析結果 | 所有步驟 (Step 2+) |
| `{{ steps[N] }}` | 第 N 步的分析結果 (例如 `{{ steps[3] }}`) | 所有步驟 |
| `{{ previous_step_all_results }}` | 所有受訪者的上一步結果 (用於 collective) | Collective 步驟 |

### 檔案列表變數
| 變數 | 說明 | 適用範圍 |
|------|------|----------|
| `{{ files }}` | 所有檔案列表 (含 id, filename, transcript) | Collective 步驟 |
| `{{ all_filenames }}` | 所有逐字稿檔案名稱陣列 | 所有步驟 |
| `{{ file_count }}` | 逐字稿總數 | 所有步驟 |

> ⚠️ **注意**：系統會自動在 System Prompt 中列出所有實際的受訪者/檔案名稱，並提示 LLM 不可虛構不存在的來源名稱。

## Step 1: 逐字稿清稿檢查

**分析類型**: 🔵 Individual (每個逐字稿獨立分析)

**目的**: 檢查並修正逐字稿中的錯字、聽錯、遺漏，但保留原話語句的情感與用詞。

### ✅ 需要使用的變數
- `{{ transcript }}` - **必須** - 傳入逐字稿內容
- `{{ filename }}` - 建議 - 識別受訪者

### ⚠️ 必須設定 Output Schema
為避免「Invalid JSON」錯誤，請在後台設定 Step 1 的 **Output Schema**：

```json
{
  "type": "object",
  "properties": {
    "受訪者": { "type": "string" },
    "清稿後逐字稿": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "時間戳": { "type": "string" },
          "說話者": { "type": "string" },
          "原話": { "type": "string" }
        }
      }
    },
    "修正說明": {
      "type": "array",
      "items": { "type": "string" }
    }
  }
}
```

### 建議 Prompt 範本 ⭐ (JSON 格式)
```
請幫我檢查以下逐字稿是否有遺漏、錯字、聽錯；如果有相同音符或錯別字請幫我更正，但請不要更正原話語句的情感與用詞。

---
【受訪者 {{ filename }} 逐字稿】
{{ transcript }}
---

【輸出格式】請以 JSON 格式輸出，包含：
1. 受訪者：受訪者識別名稱
2. 清稿後逐字稿：陣列，每項包含 { 時間戳, 說話者, 原話 }
3. 修正說明：陣列，列出所有修改（如有）

【注意】
- 保留原話的時間戳格式 (如 00:00:47)
- 不要更改原話的情感與用詞
- 若無修改，修正說明填 ["無修改"]
```

## Step 2: 身份理解

**分析類型**: 🔵 Individual

**目的**: 確認 AI 角色為質化研究專家，為後續編碼建立一致的分析視角。

### ✅ 需要使用的變數
- `{{ previous_step_result }}` - 建議 - 使用 Step 1 清稿後的逐字稿

### 建議 Prompt 範本
```
請確認AI角色，並在後續每一步驟依照此質化研究專家的角色，逐步執行後續的步驟編碼。

以下是清稿後的逐字稿：
{{ previous_step_result }}
```

## Step 3: 資料準備

**分析類型**: 🔵 Individual

**目的**: 將訪談內容分段整理成表格，方便後續編碼分析。

### ✅ 需要使用的變數
- `{{ previous_step_result }}` - **必須** - 使用前一步的結果
- `{{ filename }}` - 建議 - 標記受訪者

> ⚠️ **重要**: 此步驟需要保留原話的「時間戳」格式 (如 00:00:47)

### 建議 Prompt 範本
```
本步驟目的建立可分析的逐字稿段落表格，方便後續編碼。

以下是 {{ filename }} 的逐字稿：
{{ previous_step_result }}

1. 詳細閱讀訪談稿，了解後續分析的核心
2. 將訪談原始資料依照內容主題分段，請避免更改原話內容
3. 將結果依表格顯示：段落簡述(100字內) | 訪談者問題 | 受訪者回話

訪談的語句需要標記角色、原話、時間點（格式如：陳小姐 因為那個什麼戰後嬰兒潮... 00:00:47）
```

## Step 4: 開放性編碼（Open Coding）

**分析類型**: 🔵 Individual

**目的**: 萃取原始概念進行編碼，不先預設主題。使用 6R 框架分析。

### 6R 框架
- **Realness** (真實性)
- **Richness** (豐富性)
- **Repetition** (重複性)
- **Rationale** (合理性)
- **Repartee** (機智)
- **Regal** (權威性)

### ✅ 需要使用的變數
- `{{ previous_step_result }}` - **必須** - 使用 Step 3 的分段資料

### 建議 Prompt 範本
```
本步驟目的為萃取原始概念進行編碼，不先預設主題。

以下是分段後的訪談資料：
{{ previous_step_result }}

每段原話分析基於「6R框架」定義最多2個簡短代碼詞(15字內)，優先使用「動詞+名詞」格式。

將語意類似、相同重複的代碼詞歸類、合併，並將結果以表格顯示：
代碼詞 | 代碼定義(30字內) | 代表語句(標記時間點) | 受訪者名稱
```

## Step 5: 主軸編碼（Axial Coding）

**分析類型**: 🔵 Individual

**目的**: 將相關編碼歸納成較高層次的主題。使用 4R 框架。

### 4R 框架
- **Reciprocal** (互惠)
- **Recognizable** (可識別)
- **Responsive** (回應)
- **Resourceful** (豐富)

### ✅ 需要使用的變數
- `{{ previous_step_result }}` - **必須** - 使用 Step 4 的編碼結果

### 建議 Prompt 範本
```
根據初步編碼間的關聯性，將相關編碼歸納成較高層次的主題。

以下是開放性編碼結果：
{{ previous_step_result }}

1. 每一群命名一個主題（15字內），命名請具體、精確
2. 可使用「4R框架」進行主題開發
3. 建立表格：編號 | 主題 | 定義 | 代表語句 | 包含的代碼
```

## Step 6: 選擇性編碼（Selective Coding）

**分析類型**: 🟢 Collective (整合所有受訪者資料)

**目的**: 跨受訪者比對，合併語意相近的主題，挑選核心主題。

### ✅ 需要使用的變數
- `{{ previous_step_all_results }}` - **必須** - 取得所有受訪者的主軸編碼結果

### 建議 Prompt 範本
```
本步驟將整合所有受訪者的分析結果，進行選擇性編碼分析。

以下是各受訪者的主軸編碼結果：
{% for item in previous_step_all_results %}
### 受訪者 {{ loop.index }}
{{ item.result | dump }}
{% endfor %}

1. 列出所有受訪者的分析主題
2. 交叉比對，將語意相近的主題歸類合併
3. 依照研究目的挑選「選擇性編碼主題」
```

## Step 7: 轉換為 JTBD

**分析類型**: 🟢 Collective

**目的**: 將核心主題轉換為 JTBD (Jobs to be Done) 格式。

### JTBD 句型格式
> 當 [使用情境/角色] 時，我想要 [功能性/情感性/社會性需求]，以便/因為 [期望結果]

### ✅ 需要使用的變數
- `{{ previous_step_result }}` - **必須** - 使用 Step 6 選擇性編碼結果
- `{{ steps[3] }}` - **建議** - 取得分段後的原始語句（含時間戳）
- `{{ steps[5] }}` - 可選 - 參考主軸編碼原始資料

> ⚠️ **重要**: 必須明確要求 LLM 列出**所有**支持該 JTBD 的原始語句，而非只列一句！

### 建議回傳格式
```json
{
  "JTBD_list": [
    {
      "編號": 1,
      "JTBD": "當 [情境] 時，我想要 [需求]，以便/因為 [結果]",
      "對應主題": "主題名稱",
      "需求類型": "功能性/情感性/社會性",
      "支持的原話列表": [
        {
          "受訪者": "陳小姐",
          "原話": "我每次都要花好多時間...",
          "時間戳": "00:05:32",
          "來源檔案": "interview_001.txt"
        },
        {
          "受訪者": "林先生",
          "原話": "這個真的很麻煩，每次都要重複做...",
          "時間戳": "00:12:18",
          "來源檔案": "interview_002.txt"
        }
      ],
      "重複次數": 2,
      "優先度": "高/中/低"
    }
  ],
  "說明": "JTBD 排序依據說明..."
}
```

### 建議 Prompt 範本 ⭐ (改進版)
```
你熟悉 Jobs to be Done 方法，擅長從訪談資料中推導出使用者任務。

以下是選擇性編碼結果：
{{ previous_step_result }}

以下是各受訪者的原始訪談分段（請參考以追蹤原話來源）：
{% for item in previous_step_all_results %}
### 受訪者 {{ loop.index }}: {{ item.fileId }}
{{ item.result | dump }}
{% endfor %}

請將每個核心主題轉換為 JTBD，並嚴格遵守以下規則：

【輸出格式】
每個 JTBD 必須包含：
1. JTBD：句型「當 [情境] 時，我想要 [需求]，以便/因為 [結果]」
2. 對應主題：來自選擇性編碼的主題名稱
3. 需求類型：功能性 / 情感性 / 社會性
4. ⚠️ 支持的原話列表（陣列）：列出【所有】支持此 JTBD 的受訪者原話
   - 每個原話需包含：受訪者名稱、原話內容、時間戳、來源檔案
   - 若有多位受訪者提到類似觀點，需全部列出
5. 重複次數：有多少位受訪者提到相關觀點
6. 優先度：根據重複性與重要性判斷（高/中/低）

【排序原則】
- 重複次數多優先
- 影響程度大優先
```

## Step 8: 轉換為 HMW

**分析類型**: 🟢 Collective

**目的**: 將 JTBD 轉化為 HMW (How Might We) 問題句，用於設計發想。

### ✅ 需要使用的變數
- `{{ previous_step_result }}` - **必須** - 使用 Step 7 的 JTBD 結果

> ⚠️ **重要**: 必須保留 Step 7 的多個原話來源，而非只保留一句！

### 建議回傳格式 ⭐ (改進版 - 多來源)
為確保前端正確顯示 HMW 卡片並追蹤多個來源：

```json
{
  "HMW_questions": [
    {
      "HMW_question": "我們如何幫助使用者在資訊過載時快速找到重點？",
      "supporting_JTBD": "當使用者需要快速整理資訊時...",
      "verbatim_list": [
        {
          "受訪者": "陳小姐",
          "原話": "「我每次都要花好多時間在網路上查資料...」",
          "時間戳": "00:05:32",
          "來源檔案": "interview_001.txt"
        },
        {
          "受訪者": "林先生",
          "原話": "「資訊太多了，根本看不完...」",
          "時間戳": "00:08:45",
          "來源檔案": "interview_002.txt"
        }
      ],
      "來源受訪者數": 2,
      "priority": "高"
    }
  ],
  "explanation": "選擇這些 HMW 的原因..."
}
```

### 建議 Prompt 範本 ⭐ (改進版)
```
你是一位資深服務設計師，擅長從 JTBD 轉化出具設計價值的 HMW 問題句。

以下是 JTBD 分析結果（包含多個受訪者原話）：
{{ previous_step_result }}

請將每個 JTBD 轉為 HMW 問題句，並嚴格遵守以下規則：

【輸出格式】
每個 HMW 需包含：
1. HMW_question: HMW 問句（以「我們如何...」開頭）
2. supporting_JTBD: 支撐的 JTBD 語句
3. ⚠️ verbatim_list（陣列）：列出【所有】支持此 HMW 的受訪者原話
   - 每個原話需包含：受訪者、原話（保留原始引號）、時間戳、來源檔案
   - 若 JTBD 有多個原話來源，必須全部保留，不可只列一個
4. 來源受訪者數: 有多少位受訪者的原話支持此 HMW
5. priority: 優先度（高/中/低）

【排序原則】
- 來源受訪者數多優先（重複性高）
- 對使用者痛點影響大優先（重要性高）

【注意事項】
- 不要捏造受訪者、原話或時間戳
- 只使用上一步驟提供的實際資料
- 每個 HMW 應有明確的原話支撐
```

## 常見問題

### Q: LLM 回報「無法讀取檔案」錯誤？
**A**: 請確認 Step 1 的 prompt 有包含 `{{ transcript }}` 變數，否則 LLM 不會收到逐字稿內容。

### Q: HMW 卡片沒有顯示來源資訊？
**A**: 請在 Step 8 的 prompt 中明確要求 LLM 回傳 `source_file` 和 `timestamp` 欄位。

### Q: 如何在後續步驟取得原始逐字稿？
**A**: 使用 `{{ steps[1] }}` 可取得 Step 1 的結果（清稿後的逐字稿），或使用 `{{ steps[3] }}` 取得分段後的資料。
